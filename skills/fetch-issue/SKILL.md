## 什么时候用

任务来自 issue / 工单，需要先拿到原文再动手，而不是凭标题猜。

## 步骤

1. 用户没给编号就先调 `mcp__demo__issue_list` 看有哪些
2. 用 `mcp__demo__issue_get` 取详情（标题、正文、验收标准）
3. 拆成 3–6 步子任务，每一步写清「怎么算做完」
4. 单独列出 issue 里没写清、需要人确认的点

## 不要做什么

- 不要凭标题猜需求
- 不要在没读到 issue 正文时就开始改代码
- 不要把 MCP 的原始 JSON 整段贴出来，整理成人话

## 为什么要走 MCP 而不是猜

- issue 的「验收标准」字段决定了怎么算做完，猜不出来
- 状态可能是 closed，那就先问清是不是要 reopen 再动手
- 同一编号可能换过内容：每次都以 `issue_get` 的返回为准，不复用上一轮的记忆

## 清单长什么样（示例）

```
1. mean([]) 改成抛 ValueError（判据：新用例通过）
2. 现有 6 个用例全绿（判据：pytest -q exit 0）
3. 补一个空列表用例（判据：diff 里出现 test_mean_empty_raises）
需要确认：空列表场景是否需要给调用方一个专门异常类型？
```

## 怎么算做完了

- 有一份可执行清单，每个子任务都能对应回 issue 原文的一行
- 有「需要确认」小节的明确结论（没有就写「无」）
