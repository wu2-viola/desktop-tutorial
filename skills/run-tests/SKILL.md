## 什么时候用

用户要确认改动有没有把测试跑挂，或让你解释某个失败到底为什么。

## 步骤

1. 先跑 `python -m pytest -q`，不要一上来就 `-v` —— 输出太长会把上下文挤爆
2. 只读失败用例的 traceback，最多 3 个；通过的用例不要读
3. 每个失败按三行总结：
   - 哪个用例（文件::类::函数）
   - 期望什么（断言写的是什么）
   - 实际什么（报错那一行）
4. 结尾给一句最可能的原因，不要罗列无关的 warning

## 不要做什么

- 不要顺手改代码 —— 这一步只报告，改代码是下一个任务
- 不要重复跑同一条命令超过两次；第二次仍失败就换思路（比如单独跑一个用例）
- 不要把整段 traceback 抄进回答

## 常见错法

- 一上来 `pytest -v`：几十个 PASSED 行把失败摘要挤出上下文
- 把 `Warning` 当失败报：先看 exit code，再看 `FAILED` 行
- 只报「挂了 3 个」不报名字：主 agent 没法据此定位
- 失败原因是自己上一步改坏的却不说：先看 `git diff` 有没有你刚动的文件

## 判断「环境问题」还是「代码问题」

- `ModuleNotFoundError` / `no tests ran` / 端口占用 → 环境问题，直接说清缺什么
- `AssertionError` / `TypeError` / 逻辑不符期望 → 代码问题，给三行摘要
- 超时 → 先怀疑死循环或外部调用没 mock

## 怎么算做完了

- 给出「几红几绿」的数字
- 至多 3 条失败摘要，每条都能对应到一个具体用例
- 有一句原因判断，而不是「可能是环境问题」
